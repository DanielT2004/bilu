# StoreKit client verification

`Bilu.storekit` is a local testing catalog, not an App Store Connect configuration. Its prices are test inputs; the app always displays `Product.displayPrice`. Choose this file in the Xcode scheme's Run → Options → StoreKit Configuration to inspect StoreKit product/payment behavior. Leave it unset for App Store sandbox testing.

Purchases remain disabled unless the app's `BILUCommerceEnabled` Info.plist Boolean and the server wallet's `commerceEnabled` are both true. `BILUProEnabled` defaults to false. When both app and server Pro flags are deliberately enabled, the UI loads the monthly and annual Pro products; an active member sees App Store subscription management instead of another checkout sheet. Never enable Pro merely to demonstrate local placeholder records: use an isolated payment sandbox and a sandbox backend for end-to-end testing.

Local Xcode transactions do not carry production Apple signatures and must not be accepted by the deployed verification endpoint. `PurchaseStoreTests` injects the storefront and API to exercise payment, pending/cancelled results, durable recovery, account mismatch, and server delivery without making purchases or contacting a backend. To verify the complete Apple-signature flow, use App Store sandbox products and a separately configured sandbox backend/account after the server migration and authentication setup are ready.

The queue stores signed transactions in Application Support with file protection, excludes them from backup, and retains account ownership. Unfinished transactions are recovered on launch. Restore Purchases explicitly calls `AppStore.sync`, reconciles available transaction history, and refetches the server wallet. The server wallet is needed for consumed purchases and older OS history; no local balance is reconstructed from receipts.

Receipts for another Bilu account stay in the journal without being submitted or finished. They produce an informational notice, while `hasPendingSync` and checkout eligibility consider only the current account (or a journal read/write failure). Mixed-account history does not prevent either account from restoring or buying again.

Before opening Apple's payment sheet, the client persists an account/product approval reminder. It survives app termination, is cleared on a definite cancellation/failure, and remains when StoreKit reports `.pending`. A matching new verified transaction resolves it. Older purchase history cannot resolve a newer reminder. The reminder does not expire on a local timer, and empty unfinished/history sequences never imply a decline.

Apple documents that a successful pending purchase arrives through transaction updates, while a declined Ask to Buy request does not produce a transaction. The UI therefore offers a separate recovery action: after checking with the parent/guardian or App Store that the request was declined/cancelled, the user confirms clearing the reminder. The app first synchronizes StoreKit and reconciles any transactions; if that succeeds, it clears only the current account's reminder. Clearing does not cancel an Apple request and never starts another purchase. If the original request still exists, approving it can still charge the original account; a new purchase requires a separate explicit action. See [pending purchase results](https://developer.apple.com/documentation/storekit/product/purchaseresult/pending), [Ask to Buy testing](https://developer.apple.com/documentation/storekit/testing-ask-to-buy-in-xcode), and [Apple's parent/guardian instructions](https://support.apple.com/en-gb/105055).

The dependency-injected tests cover approval persistence, empty-history retention, old-history protection, explicit recovery without repurchase, and mixed-account restoration. They are not evidence of Apple's payment-sheet behavior. Apple lists approving/rejecting an Ask to Buy request as supported in local Xcode StoreKit testing, **not sandbox**; manually exercise both outcomes with `Bilu.storekit`, terminate/relaunch while pending, and verify the later approved transaction reconciles exactly once. Device/App Store behavior remains an external release check. See [Apple's testing environment matrix](https://developer.apple.com/documentation/storekit/testing-at-all-stages-of-development-with-xcode-and-the-sandbox).

Apple API references: [transaction updates](https://developer.apple.com/documentation/storekit/transaction/updates), [unfinished transactions](https://developer.apple.com/documentation/storekit/transaction/unfinished), [finish](https://developer.apple.com/documentation/storekit/transaction/finish()), [account tokens](https://developer.apple.com/documentation/storekit/product/purchaseoption/appaccounttoken(_:)), and [consumable history](https://developer.apple.com/documentation/bundleresources/information-property-list/skincludeconsumableinapppurchasehistory).
